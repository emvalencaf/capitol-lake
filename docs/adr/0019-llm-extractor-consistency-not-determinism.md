# LLM extractor is a distinct benchmark path scored by consistency, not determinism

`run_house_eval.py`'s existing determinism check requires every extractor to produce byte-identical output across two runs of the same bytes — true for `extract_digital`/`extract_scanned` since they're pure parsing. Adding an LLM-based extractor for benchmarking against them (reusing the Groq/LM Studio providers already in `shared/llm_providers.py`) breaks that assumption: model output varies run to run even on identical input, and that variance is itself real signal about a model's reliability, not a bug to hide.

Decided: the LLM extractor (`extract_llm`) is kept as a concept distinct from the existing `llm_fallback` — `llm_fallback` patches individual null/low-confidence fields after a rule-based extractor runs, while `extract_llm` produces every field itself, standing alongside `extract_digital`/`extract_scanned` purely for benchmarking, never wired into `extract_house_filing`. The determinism check is skipped for it and replaced with an optional **consistency** check: `--llm-runs N` (default 1, meaning skipped) re-extracts the same filing N times and reports the average pairwise field-score across all run pairs, per field and overall, using the same `score_filing` machinery as the accuracy report rather than a binary identical/not-identical verdict. Call failures (rate limits, timeouts, malformed JSON) are scored as a total miss on that filing, same as any other extraction failure, with no automatic retries — an LLM's failure rate under real provider conditions is part of what the benchmark is measuring.

## Considered Options

- **Require determinism via `temperature=0`**: rejected — even at temperature 0, provider-side nondeterminism (batching, hardware) isn't fully eliminated, and treating any drift as a hard failure would make most models unbenchmarkable rather than surfacing how consistent they actually are.
- **Retry on transient failures before scoring**: rejected for now — retrying would mask exactly the reliability differences (rate limits, timeouts) a benchmark should report; can be added later as an explicit `--retries` flag if it turns out to matter.
