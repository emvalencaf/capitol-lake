# Every collector gets its "already collected" set from one S3 listing, not a GetObject per entry; Senate now skips a known id too

ADR-0017 made `collect_house` skip fetching a `doc_id` already on record, but kept checking that via `read_existing_sha256(meta_key)` — one `s3:GetObject` per index entry, reading and JSON-parsing a `.meta.json` sidecar just to test it for existence. That call's actual return value (the prior sha256) had stopped being used for anything: the skip path only ever checked `is not None`, and the write path always called `bronze_write(..., existing_sha256=None, ...)` unconditionally, since a fetched `doc_id` is by definition one `known_doc_ids` didn't already have. Paying for a full object read (and a JSON parse) to answer a plain existence question was wasted work, multiplied by every entry in the year's index.

Decided: `collect_house`, `collect_senate`, and `run_senate_efd_session` now take a `known_doc_ids: Callable[[], set[str]]` in place of `read_existing_sha256`, called **once** per run rather than once per entry. Each handler implements it as a single (paginated) `s3:ListObjectsV2` over the relevant bronze prefix, parsing every returned key through `shared.keys.parse_bronze_key` (which recovers the same `doc_id` whether the key is the original object, its `.meta.json` sidecar, or a versioned `<doc_id>.<sha256[:8]>.<ext>` key from before this policy existed) into a `set`. `house_collect/handler.py` scopes its listing to `bronze/house/year=<year>/` (one year, matching what `collect_house` operates over); `senate_collect/handler.py` and `senate_collect_automated/handler.py` both list the whole `bronze/senate/` prefix (every year), since a captured search response or a lookback window can span a year boundary — cheap given the Senate corpus is far smaller than House's.

Decided further: **Senate now gets the same skip-entirely policy House got in ADR-0017** — `collect_senate` and `run_senate_efd_session` both skip a known filing UUID with no fetch (and, for the automated path, no browser page navigation at all, which also means no Akamai classification is needed for a skipped entry). Unlike ADR-0017's House decision, this is **not** backed by independent primary-source research: it rests entirely on this repo's own pre-existing, unverified assumption (`shared/senate_index.py`'s comment, and `collect_senate`'s prior docstring) that a Senate eFD amendment always gets its own separate UUID rather than reusing the original filing's. `docs/research/house-ptr-amendment-doc-id-behavior.md` explicitly declined to verify the Senate side (out of scope for that research pass). This was a deliberate, informed choice to accept the same class of risk as House without the same evidence behind it, made because re-verifying every known Senate filing costs real browser-session time (and, for the automated path, more Akamai-facing page loads than necessary) for a benefit — catching a silently-replaced UUID — that has no known precedent.

Every affected return shape's `noop` key/field is renamed `skipped` (there is no hash comparison happening to call a no-op anymore): `collect_house`'s and `collect_senate`'s return dicts, and `SenateEfdSessionResult.noop` → `.skipped`. Each handler's wide-event field is `skipped_count`, and `on_progress`'s `action` is `"skip"` in place of `"noop"`.

If evidence ever surfaces that a Senate eFD amendment can reuse an existing UUID with different content, the fetch-and-hash-compare behavior ADR-0017/this ADR removed can be reinstated for Senate specifically (or narrowed to it) without touching House.
