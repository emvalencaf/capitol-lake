# Senate's bronze-to-extract chain goes through extract's own SQS queue, not a direct S3-to-Lambda invoke

Per #18/#43's orchestration shape, House's scheduled collector chains into `extract` over SQS: `house_collect`'s handler builds `extract_queue_message` and sends it to extract's own queue, so a failed extract invocation gets extract's queue's redrive policy — retried up to `max_receive_count` times, then dead-lettered to extract's DLQ for a human to inspect. Senate has no scheduled collector, so its bronze writes (manual upload or `senate_collect`/`senate_collect_automated`) instead relied on an S3 event notification on the bronze bucket invoking `extract`'s Lambda function directly (`aws_lambda_permission` + `aws_s3_bucket_notification`'s `lambda_function` block, scoped to `bronze/senate/*.html`).

That asymmetry meant a Senate-triggered extract failure had nothing to retry or dead-letter: a direct S3-to-Lambda invoke carries no SQS message, so `shared.orchestration.BronzeKeyRecord.message_id` was always `None` for an S3-sourced record, and a handler's `batchItemFailures` reporting has nothing to report against. A transient extract failure on a Senate filing (a rate-limited OpenFIGI/EDGAR call, a flaky LLM-fallback provider) simply failed once and was gone, with no automatic retry and no DLQ trail — unlike the identical failure on a House filing.

Decided: the bronze bucket's S3 event notification now targets extract's own SQS queue (`aws_s3_bucket_notification`'s `queue` block) instead of invoking the Lambda directly, with an `aws_sqs_queue_policy` scoping `s3.amazonaws.com`'s `sqs:SendMessage` to the bronze bucket's ARN. This gives Senate-triggered messages the same retry/DLQ handling House's own messages already had, at the cost of the SQS record's `body` sometimes being a raw S3 event notification (itself a `{"Records": [...]}` document) instead of House's `{"bronze_key": ...}` shape. `shared.orchestration.bronze_key_records_from_event` was extended to unpack that nested shape, pairing every bronze key it finds with the *outer* SQS record's `messageId` — the actual fix, since a redelivery of that outer message is what a real retry would look like.
