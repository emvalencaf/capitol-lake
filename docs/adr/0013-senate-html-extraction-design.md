# Senate HTML extraction: no doc-id cross-check, Exchange as one row with two legs

Unlike a House PTR (a text-layer PDF whose own footer prints `Filing ID #<doc_id>`, letting `extract_house_filing` raise `DocIdMismatchError` when it disagrees with the bronze key), a Senate `/ptr/` filing page carries no identifier of its own anywhere in its HTML — the filing's UUID exists only in the eFD search result's URL, already captured as the bronze key's `doc_id` before the page is ever fetched. There is no second source to cross-check against.

Decided: `extract_senate_filing` takes `doc_id` from the bronze key alone and performs no integrity check analogous to `DocIdMismatchError`. This is a real, if narrow, loss of the safety net House's extractor has — worth knowing before anyone goes looking for why Senate rows have no such guard.

Separately, the Senate PTR table renders an `Exchange` transaction (one asset given up, a different one received) as a single table row whose asset cell holds two lines of text, e.g. `"AvalonBay ... (AVB) (Exchanged)"` / `"VMRK - Vivmark ... (Received)"` — no structured split exists in the source. Decided: this stays one `Transaction` row, matching the source; the asset given up lands in `asset_description` (what `asset_type`/`ticker` actually describe), and the asset received is kept verbatim in `description`. The same `description` field also holds a Senate option row's `Option Type` / `Strike price` / `Expires` block when present (never both at once in any sampled filing). `notification_date`, `filing_status` and `sub_owner` have no structured source in the Senate page at all — unlike House, where they're printed labelled lines — and stay null rather than parsed out of the free-text `Comment` column, which is dropped entirely (see ADR 0002's null-over-guessed precedent).
